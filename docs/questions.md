## 1. 配网、管理与安全

### Q01：16 位校验码太长，能否简化？

**已实现：**BLE PoP 改为每次会话重新生成的 **6 位纯数字**，保留前导零；页面使用数字键盘输入。短码是易用性取舍，不宣称与长随机码等强。**HTTP 登录仍使用另一组每次会话生成的 16 位十六进制密码**，不能把 BLE 的改动说成所有密码都已缩短。

### Q02：首次配网到底是什么体验？

**已实现，待实机：**设备进入初始化，显示设备名和六位码；用户用支持 Web Bluetooth 的 Chrome/Edge 打开 HTTPS Pages，选择设备、验证、填写或扫描 Wi-Fi，再提交。新版页面收到**应用配置保存 ACK**才报告成功；也可以通过 BLE 手动设置时间。手机不必切到设备热点，设备不会创建热点。普通 iPhone/iPad 浏览器通常不支持该网页 BLE 流程。

**版本修正：**早期只能查询 SDK Connected/IP，不能确认应用 NVS 保存；新版自定义 `clock-control` 已补应用保存 ACK。新页面与固件必须配套，不能混用旧版说明。

### Q03：第二次进入还需要配网吗？能不能以后直接访问 LAN 网页？

**已实现：**保存的 Wi-Fi 不会因关机丢失，不需要每次重新配网。设备运行时长按中键打开选单，选择 LAN 管理；电池 PMU 关机时先用 PWR 上电。管理连续五分钟无用户交互后返回时钟并关闭网络。

**尚未实现常驻访问：**USB 时钟模式也不是常驻 HTTP。关机设备无法通过网页唤醒。常驻 LAN 需要另定 USB/电池供电策略，不能在未确定功耗取舍时默认启用。

### Q04：想更改 Wi-Fi 信息，流程是什么？

**已实现，待实机：**长按中键打开选单 → 蓝牙管理 → 打开 Pages、输入本次六位码 → 提交新 Wi-Fi。只有新网络验证成功并保存后才报告保存成功。旧路由器不可用不妨碍 BLE。

需要强制重新初始化时，按住上键再 PWR 开机；或者从选单选择初始化并完成额外确认。初始化不是清空整机、RTC 或 TF 卡。当前 LAN 页面不提交 Wi-Fi 凭据。

### Q05：Wi-Fi 无法连接、密码错误或管理期间掉线怎么办？

**当前已实现：**初始化失败仍留初始模式，BLE 窗口暂停后中键重试；LAN 连接失败有屏幕反馈，会话内最多三次尝试、间隔十秒，掉线可在预算内重连，仍可用选单切换模式。自动每日校时失败不在当天密集重试，RTC 继续走时。

首次 NTP 失败且 RTC 无效时，仍可留在初始化，通过 BLE 手动设时。每日自动校时检查本身仍依赖有效 RTC，不能说无效日期下一定会自动恢复。

**版本修正：**早期“没有失败提示/没有重连”“配网失败退时钟”“LAN 另有十五分钟总上限”已不代表当前实现。当前 LAN 按闲置五分钟退出，主动交互可续期，状态轮询不续期。

### Q06：安全验证在哪里执行，会不会很耗电？

**代码确认，电量待实测：**网页格式校验在手机/电脑；Security1 握手在配网时执行；HTTP 认证只在管理中执行，传感器 CRC 在采样时执行。不能把验证代码数量当作功耗。优先测无线开启时长、启动、SD 和屏幕刷新；没有本板数据证明安全运算的具体占比。

### Q07：有限状态机有没有梳理出来？

**已有文档：**见 [三模式状态机](state-machine.md)和[按键/交互规则](interaction.md)。状态机记录实际转换与失败恢复；初始化、时钟、管理是三个业务模式，菜单和一次性诊断不是新增模式。旧讨论图不能替代最新状态机；任何图都不等于实机验收。

## 2. 整机供电与 RTC 备用电池

### Q08：墨水屏的供电方案，文档里有写吗？

**代码/资料确认，电源轨待实机：**当前按官方示例将屏幕映射到 PMU **ALDO3、3.3V**。`EPD_Init()` 开启供电，刷新结束后 `EPD_Sleep()` 发休眠命令并关闭 ALDO3。图像在断电后保留。**屏幕断电不等于 ESP32 或整机关机**；主控可以在屏幕断电时继续运行 LAN。

### Q09：整台机器如何供电？

**资料确认：**USB-C 5V 或单节 3.7V 主锂电池，经板载 PMU 管理供电和充电。当前固件电池模式每分钟更新后 PMU 关机；USB 时保持主控运行，仍按业务短时开启无线。完整电源轨、供电切换及静态电流尚未实测。官方资料称 TG28，官方示例使用 AXP2101 接口；不能因此推断任意 AXP2101 板都兼容。

### Q10：RTC 备用电池是自带的吗？

**待确认：**官方明确的是“预留 MX1.25 RTC 备用电池接口”，没有凭这些资料确认随板附赠电池。是否包含应看购买套餐及实际包装；接口存在不等于电池已经装好。

### Q11：RTC 备用电池一般多大，是什么规格？

**通用示例，不是本板采购规格：**CR1220 约 12.5×2.0mm、35–40mAh，不可充电；CR2032 约 20×3.2mm、220mAh，不可充电；ML1220 约 12.5×2.0mm、17mAh，可充电但须符合自身充电条件。容量随厂家变化。

本板是带线的 MX1.25 两针接口，不是已确认的裸纽扣电池座。**电池型号、插头极性和适配充电条件仍需核对，不凭“3V RTC 电池”直接采购。**

### Q12：官方文档和硬件资料链接在哪里？

- [板卡介绍](https://docs.waveshare.net/ESP32-S3-ePaper-3.97)
- [资料汇总](https://docs.waveshare.net/ESP32-S3-ePaper-3.97/Resources-And-Documents)
- [板卡原理图 PDF](https://www.waveshare.net/w/upload/a/ad/ESP32-S3_e-Paper-3.97-schematic.pdf)
- [TG28 手册 PDF](https://www.waveshare.net/w/upload/1/19/TG28_Datasheet_V1.0_en.pdf)
- [屏幕手册 PDF](https://www.waveshare.net/w/upload/f/fa/3.97inch_e-Paper.pdf)

部分直链有浏览器验证。TG28 结论来自用户提供的本地 PDF；屏幕手册另核对了公开归档，不把验证页当 PDF。

### Q13：TG28 手册对备用电池到底说了什么？

**手册确认：**第 7 页：27 脚 VBackup、28 脚 VRTC。第 23 页 §6.12.2：只有备用电池时，VBackup 为 RTCLDO1 提供电源；可用 **100μA** 小电流充电。第 27 页：`REG18[2]` 控制备用充电，默认关闭。第 39 页：`REG6A` 终止电压 **2.6–3.3V**、0.1V 一档，默认 2.9V。

当前固件设为 **3.0V 并开启充电**。手册没有因此指定电池型号、容量或外形，不能用这些参数代替电池自己的规格书。

### Q14：“RTC 备用电池”究竟是什么？

**用途定义：**主电池和 USB 都断开后，单独维持 RTC 走时的小电源。它不负责运行主控、Wi-Fi 或刷新屏幕。正常主锂电池仍连接的分钟关机时钟，按官方设计由保留的 RTC 电源维持走时，并不必需另接备用电池。

### Q15：主电池与备用电池怎么区分？

**按接口和用途区分，不按大小：**主电池接整机锂电接口，给整个系统供电；备用电池接 RTC 备用接口，只负责失去主电源后的保时。固件主电池充电设置为 4.2V/200mA，备用为 3.0V/100μA。两接口即使外形同为 MX1.25，也不能互换。

### Q16：能否理解为 RTC 备用电池也是可充电锂电池？

**有条件：**在当前开启备用充电的配置下，应使用允许 **3.0V、100μA** 条件充电的电池；但尚未确定具体化学体系和型号。不是把普通 3.7V/4.2V 主锂电池接过去。“RTC 备用电池”只是用途名称，本身不保证可充电；**不能在开启充电时直接接 CR 系列不可充电电池**。

### Q17：这种小型备用电池一般多少钱？

**非实时价格参考：**讨论中的粗略范围为几元到二十多元；普通品牌约 3–10 元，品牌产品约 10–25 元，带线和插头可能另加成本。这不是实时报价或已确认适配型号的采购建议，先核实规格再购买。

## 3. TF 卡、内部存储与耗电

### Q18：没有 TF 卡能存 Wi-Fi 吗？

**已实现：**Wi-Fi 名称/密码保存在板载 Flash 的 NVS，断电保留，不依赖 TF。当前新配置用单个带版本记录保存。TF 是画面缓存用途；无卡时仍可配网、保存配置和运行时钟，刷新回退为全刷。

### Q19：插 TF 卡会更省电吗？

**尚无净收益实测：**有卡能保存旧帧并沿用双次局刷，无卡当前回退全刷；卡本身有初始化、读写和等待电流。哪种整周期更省，取决于屏幕省下的电是否超过存储及主控延时增加的电，不能把插卡当作硬件省电开关。

### Q20：官方文档有没有说插卡更省电？

**没有查到对照结论：**官方综合示例要求插入配套 SD 文件，并标称时钟模式约 1500mAh 电池工作十五天以上，但未提供插卡/不插卡对比和完整测试条件。保存旧帧供后续局刷是示例代码行为，不是已给出省电比例的测量报告。

### Q21：旧帧可以不存图片，靠计算重建吗？

**可研究：**固定字体/布局下，保存上次显示的时间、温湿度、电量等少量状态，再绘制上一帧，理论上不必存完整 48000 字节图片。过去的传感器读数不能从当前读数反推；校时、漏更新或管理画面也使“当前减一分钟”不可靠。PMU 关机丢 RAM，少量状态仍需可靠保存。尚未实现或验证净节能。

### Q22：每分钟写内部 Flash 会磨损吗，TF 是否更好？

**有磨损，但优劣未定量：**每分钟一次是约 1440 次/日，NVS 有磨损均衡，底层擦除次数不等于应用写调用次数；TF 也有寿命，且通常便于更换。低频保存 Wi-Fi 不属于主要磨损负担。

**纠正早期措辞：**不能仅凭频繁写入就断言 TF 必然更可靠、更省电；尚未对具体 Flash 分区、磨损均衡、卡品质和断电行为作寿命评估。暂保留现有 TF 缓存是避免未验证重构，不是已经证明最优。

### Q23：时间和温湿度固定在几个矩形里，能否不知道旧图也局刷？

**方向合理，尚未验证：**固定窗口减少变化范围，不自动解决旧帧基准。若控制器保留旧图，或能可靠地把指定窗口擦成已知背景再重画，可能不需要主控保存旧图；本项目每轮关闭屏幕电源，不能依赖 RAM 保留。当前移植驱动仅实现整屏范围局刷，不能将“窗口填白数据”直接等同于物理擦白。

### Q24：固定窗口无 TF 和当前有 TF，估计哪个更耗电？

**条件判断：**当前有 TF 已是两次局刷，不能把无 TF 的“擦白＋重画”全部算作新增。如果固定窗口同样两次且更快，预计有优势；如果擦白需要更长波形或更多刷新，可能反而更耗。假设整机 80mA，每分钟多工作 0.5 秒就多约 16mAh/日；该数只是敏感性换算，不是本板结果。

### Q25：TF 卡容量大小影响电耗吗？

**没有单调关系证据：**卡型号、控制器、工作模式、初始化和写入尾延迟比 GB 数更有解释力。项目只读写固定缓存，不会因卡大而按容量多读写。16/32GB FAT32 是便于使用的选择，不是已确认最省电的容量；不为省电专门寻找旧小卡。

### Q26：TF 电耗调研查到了什么？

**有外部证据，不是本板实测：**Gough 的 3.3V/12MHz SPI 测试中，三张卡活动均值约 20–24mA，测试结束后仍供电约 0.15、1.25、1.45mA；另一记录器实验的保存电荷卡间差异超过五倍。厂商规格另区分典型与最大电流。不能把 SPI、UHS-I 或型号历史数据直接套入本项目 4-bit SDMMC/最高 40MHz。

完整引用、条件与换算见 [TF 电耗调研](sd-card-power.md)。每轮总电荷 5/20/50mA·s 对应卡端约 2/8/20mAh/日，只是换算情景，不是测得范围。卡端电量也不等同于电池端电量。

## 4. 省电模式、测量和续航

### Q27：文档有没有整机或器件电耗信息？

**有参考值，没有完整本板预算：**Waveshare 给时钟十五天以上的续航标称。TG28 第 16 页在仅电池、BATFET 关闭、只开 RTC LDO 的条件下给典型约 40μA；这是 PMU 条件参数，不是本板实测关机电流。卡厂商另有读写/Idle 规格。不能简单相加为准确续航。

### Q28：机器有没有更低功耗模式可以切换？

**硬件有能力，固件未提供已验证省电档：**TG28 第 17 页 Sleep/Wakeup 允许配置部分电源轨；ESP32 支持 Light-sleep/Deep-sleep。当前电池时钟采用 PMU 关机。其他方案能否降低总电量，须比较整周期，不只看某个芯片的睡眠电流；不要未经板级核对就关闭电源轨。

### Q29：PMU 关机与 ESP32 深睡可以估算比较吗？

**可以作收支模型，不能当作测量。先纠正：Deep-sleep 唤醒也会重新启动、进入应用初始化，不像 Light-sleep 原地恢复；不会自动免掉 SD 初始化，也不能默认保留普通 RAM/PSRAM 中的 48KB 帧。**

讨论示例统一假设每分钟活动电池端 80mA、原活动 3 秒、PMU 等待按 40μA、深睡整板按 200μA。得到：

| 情景 | 估算日耗电 |
| --- | ---: |
| PMU，活动 3 秒 | 96.9mAh |
| 深睡，仍活动 3 秒 | 100.6mAh |
| 深睡，活动缩短为 2.8 秒 | 94.2mAh |
| 深睡，活动缩短为 2.5 秒 | 84.6mAh |

这些输入均未在本板测得。沿用同一模型，深睡整板为 100/200/500/1000μA 时，每轮约要省 43/114/330/693ms 才抵消额外等待电量。整板深睡不能只填 ESP32 裸芯片的数值。

### Q30：文档提供了如何测量功耗的方案吗？

**没有查到板卡专用完整测量教程：**TG28 第 22 页 ADC 公开的是电压/温度，E-Gauge 提供电量百分比与电压；不能据此认为可直接读取每分钟精确耗电。输入限流或充电电流设置也不是实际电流。

建议（不是官方原文）：在主电池与板卡主电池接口之间接电流记录/功耗分析仪，拔掉 USB，记录完整周期并积分，仪器须覆盖 μA级底电流到数百 mA级活动及短脉冲。普通 USB 表会改变供电路径和固件分支；普通万用表不适合完整瞬态积分。不能直接用拔 TF 前后的整机差值当卡功耗，因为无卡会改变刷新策略。

### Q31：算上 SD 初始化，PMU 关机还是深睡更省？

**当前倾向 PMU，尚未实测：**若深睡也关卡电源，两者都要初始化；若保留卡供电，还要付出每分钟余下等待时间的电流，并专门实现恢复路径。假设卡端每轮省 10mA·s 初始化、等待 57 秒，则仅卡的额外电流需低于约 175μA 才抵消；尚未算深睡其它开销。不是“深睡自动省初始化”。

### Q32：按当前 PMU 关机代码，估计能有多少续航？

**估算口径：1500mAh 电池、可用容量保守按 1200mAh、每分钟更新、有 TF、每日一次校时、很少进入管理，先按约两周、粗略 10–20 天规划，不承诺。**

假设活动平均 80mA、关机和每日联网另预算 3mAh/日：

| 每分钟摊销后的平均活动时间 | 估算日耗电 | 1200mAh 可用容量下续航 |
| --- | ---: | ---: |
| 1.5 秒 | 51mAh | 约 24 天 |
| 2 秒 | 67mAh | 约 18 天 |
| 3 秒 | 99mAh | 约 12 天 |
| 4 秒 | 131mAh | 约 9 天 |

时间须包含启动、SD、采样、两次局刷，并摊入整点/半点全刷。80mA、活动秒数及可用容量都不是本板测量；管理时长、失败重试、低温、老化或更慢卡会改变结果。普通 RTC 分钟启动不额外等待手动进入时钟后的五秒交互窗口。不能因为删了音频就保证超过官方标称。

## 5. 灰度、旧帧与单次局刷

### Q33：墨水屏支持灰度吗？

**已实现三项全局渲染：**LAN 可选择无灰度、线性灰度、轮廓匹配四灰，覆盖全部电子纸文字。两种灰度都只用黑／深灰／浅灰／白四档，并采用整屏刷新，不代表支持四灰局刷。默认无灰度，实机色阶与刷新仍待验收；见 [渲染设置](rendering.md)。

### Q34：四灰度会增加很多耗电吗？

**不按灰阶倍数增加：**静态保留图像仍可断电。差异在波形、耗时、数据与主控运行时间；不能把四级灰度说成耗电四倍，也不能承诺可沿用黑白局刷。以 80mA 假设换算，每分钟多 0.5/1 秒约多 16/32mAh/日，并非灰度实测。默认保持无灰度；用户可选择四灰整屏更新，灰模式不读写旧帧 SD 缓存。实际净电耗仍未知；灰度背景与黑白窗口混刷未启用、稳定性尚未验证。

### Q35：当前为什么是两次黑白局刷，而不是一次？

**无灰度模式代码确认：**屏幕重新上电后，用 TF 旧帧调用一次局刷，再用新帧调用一次。当前 `EPD_Display_Partial()` 把写 RAM 和显示激活放在一起，因此第一遍也确实驱动了屏幕，不只是写数据。它沿用示例的保守旧帧恢复方式，**不是已经证明不可减少的硬件要求**。

### Q36：控制器是否支持只写旧帧 RAM，最后一次局刷？

**机制有明确依据，目标冷启动流程待实机：**官方屏幕手册确认 SSD1677；同规格 3.97 英寸 GxEPD2 驱动分别用 `0x26` 写 previous、`0x24` 写 current，再单独触发更新。同板 Free-Ink SDK 也提供只写旧 RAM 的接口。

但是成熟驱动默认要求断电后首次全刷，不能把“RAM API 存在”当作“本板 PMU 真断电恢复已可靠”。候选是初始化 → 写准确旧帧 → 写新帧 → 一次差分激活 → 休眠断电。仍需 TF/可靠旧帧，不是忽略旧画面；两帧仍各 48000 字节，SPI 数据和总耗电不因少一次激活就减半。

寄存器、固定源码版本、限制与最小验证见 [单次局刷调研](single-refresh-research.md)。目前未改为单刷默认路径。

## 6. 结论修正与待办

### 不再沿用的旧说法

| 早期说法/容易造成的理解 | 当前应采用的结论 |
| --- | --- |
| BLE 码需要手输 16 位 | 已改六位纯数字；HTTP 密码仍是另一回事 |
| 网页拿到 IP 无法确认应用保存 | 新版 `clock-control` 已有应用保存 ACK；旧 SDK GetStatus 本身仍没有 |
| 配网失败退时钟，LAN 无重连/无失败提示，最多十五分钟 | 已按三模式及有限重连修改；当前 LAN 闲置五分钟退出，无十五分钟总上限 |
| 每次 USB 启动必须阻塞等串口十秒 | 当前 USB 时间入口非阻塞，不再强制等待 |
| RTC 备用电池已经自带/就是某型号锂电池 | 仅确认接口和充电能力，附赠与型号未确认 |
| 插 TF 必然更省电、寿命必然更好 | 没有完成具体系统的功耗和寿命对照 |
| 深睡醒来就省掉整套初始化 | Deep-sleep 同样重新启动，需专门优化才可能减少工作 |
| 局刷一定要存整张图、一定要刷两次 | 可研究状态重建/窗口/旧 RAM 恢复；单次激活有机制依据，冷启动可靠性未验证 |
| 约两周或任何模型数值就是实测续航 | 都是带假设的规划数字，必须用实机电量核验 |

### 还没有确定的事项

- RTC 备用电池的配套型号、极性、是否附赠，以及实际板级充电路径。
- USB/电池是否都要求常驻 LAN；本次没有改变当前短时管理策略。
- 整机关机与深睡电流、普通/全刷分钟的总电量、SD 初始化与长延迟。
- 断电后恢复两块 RAM、只一次局刷的残影和可靠性；真正窗口擦白与四灰度混刷能力。
- 全部真实按键、BLE、路由器、OTA 断电回滚和电池续航仍待上板验收。
